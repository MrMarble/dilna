# Does pi's extension mechanism cover ADR-0017's background-work/subagent/cron surface?

Research for wayfinder ticket [Research: pi's extension mechanism vs. ADR-0017's background-work/subagent/cron surface](https://github.com/MrMarble/dilna/issues/101), child of map [#93](https://github.com/MrMarble/dilna/issues/93). Follows up [Design: sessions/manager.ts dispatch swap](https://github.com/MrMarble/dilna/issues/97)'s finding that `pi-agent-core`/`pi-coding-agent` have no built-in equivalent of ADR-0017's background-work-aware idle timer, the Task-tool subagent feature, or `ScheduleWakeup`/`CronCreate`/`/loop`.

Grounded three independent ways: (1) direct source inspection of `earendil-works/pi` cloned fresh (`git clone https://github.com/earendil-works/pi`, 2026-08-28, default branch) — the pi-manager-dispatch ticket already confirmed zero background-task/subagent/cron matches in the *installed npm packages*; this doc reads the actual example extension shipped in the source repo, `packages/coding-agent/examples/extensions/subagent/`. (2) OpenClaw's own published integration docs (`open-claw.bot/docs/platforms/pi/`), the real-world consumer pi's own site points at. (3) OpenClaw's own product docs for the specific features in question (`open-claw.bot/docs/gateway/heartbeat/`, `open-claw.bot/docs/tools/automation/cron-jobs/`, `open-claw.bot/docs/tools/automation/cron-vs-heartbeat/`).

**Purpose:** answer the ticket's question directly enough that map #93 can decide whether to accept the ADR-0017 gap for v1 or scope in a replacement, without needing to prototype anything first.

## 1. Confirmed a third way: pi ships none of this, by design, and every real consumer builds it themselves

The subagent example's own README states its mechanism plainly: *"This tool executes a separate `pi` subprocess with a delegated system prompt and tool/model configuration."* Reading `index.ts` in full confirms it: `runSingleAgent()` calls `node:child_process`'s `spawn()` on the `pi` **CLI binary itself** (`getPiInvocation()` resolves `process.execPath`/`pi` and re-invokes it with `--mode json -p --no-session --model ... --append-system-prompt <tmpfile>`), then parses newline-delimited JSON events off its stdout (`message_end`/`tool_result_end`). The extension registers this as a tool via `pi.registerTool(...)`, an API from `@earendil-works/pi-coding-agent`'s `ExtensionAPI` — i.e. the "subagent" capability isn't provided by `pi-agent-core`'s `Agent` at all; it's ~600 lines of **application code** the example ships, wired in through `pi-coding-agent`'s extension-loading mechanism, that happens to reach for "spawn another `pi` CLI process" as its implementation strategy.

OpenClaw's own docs (`open-claw.bot/docs/platforms/pi/`) independently confirm the same shape from the consumer side. OpenClaw embeds pi **in-process**, not via subprocess — *"Instead of spawning pi as a subprocess or using RPC mode, you directly import and instantiate pi's `AgentSession` via `createAgentSession()`"* (`runEmbeddedPiAgent()` in `pi-embedded-runner/run.ts`) — but for background/scheduled work it lists three pieces of **its own infrastructure**, not anything from pi: a `cron-tool.ts`, a "Background Tasks" subagent-spawning mechanism, and a heartbeat mechanism. None of these ship in `pi-agent-core`/`pi-coding-agent` — OpenClaw built all three at its own application layer, the same way the subagent example built its subprocess-spawning tool at its.

**Net: "build it with extensions" (pi's own stated philosophy — no sub-agents/background-bash/to-dos built in, by design) is accurate, but "extension" here means ordinary application code registered as a tool, not a pi-provided subsystem that does this for you.** Every real implementation surveyed — the official example, and the one production consumer with public docs — independently arrived at "the host application writes this itself." That's true confirmation the surface doesn't exist in pi, not merely an absence of evidence.

## 2. Subagents and background-bash: buildable as custom tools, and dilna has a cheaper path than either reference example

A **subagent-shaped tool** is buildable as a plain custom `AgentTool` (the same interface the six fs tools and `bash` already use, per `docs/research/pi-tool-confinement.md`) whose `execute()` constructs a *second* `pi-agent-core` `Agent` instance, runs `.prompt(task)` on it, and returns the final assistant text. This is **cheaper than either reference implementation dilna could otherwise copy**: the official example spawns a whole `pi` CLI subprocess per call (parsing JSON-lines stdout, needing the `pi` binary resolvable on `PATH`); OpenClaw's `AgentSession`-based approach pulls in `pi-coding-agent`'s `SessionManager`/settings/resource-loader layer. dilna's `pi.ts` already constructs bare `Agent` instances directly (per map #93's own scoping, reaffirmed by [#96](https://github.com/MrMarble/dilna/issues/96)/[#95](https://github.com/MrMarble/dilna/issues/95)'s designs) — a subagent tool for dilna is just "construct one more `Agent`, in-process, no subprocess and no `pi-coding-agent` product layer needed at all." Neither reference example's approach is one dilna should imitate; both solve a problem (no direct `Agent` access from where the tool runs) dilna doesn't have.

**Background bash** (a `bash_background`/`bash_poll`-shaped pair of tools, mirroring Claude Code's `run_in_background`) is the same story: pi ships one synchronous `bash` tool (per #95's confinement research) with no backgrounding variant, and neither the subagent example nor OpenClaw's docs describe pi providing one — it would be two more custom tools, no different in kind from the subagent tool above.

**Neither of these needs `pi-coding-agent`'s `ExtensionAPI`/`registerTool` mechanism at all.** That API is how a `pi`-CLI-hosted extension registers a tool into the CLI product's own tool list; dilna isn't building a `pi`-CLI extension, it's building `pi.ts` as its own direct integration against `pi-agent-core`'s `Agent`, which takes tools as a plain array on `AgentState.tools`/`AgentOptions`. Both tools, if built, are just more entries in that array — exactly the same shape dilna already needs for the six fs tools and `bash`.

## 3. Cron/`ScheduleWakeup`/heartbeat: the one piece that genuinely needs new infrastructure, confirmed by how OpenClaw actually built it

OpenClaw's dedicated docs (`open-claw.bot/docs/gateway/heartbeat/`, `open-claw.bot/docs/tools/automation/cron-jobs/`) describe this concretely:

- **Heartbeat**: "a scheduled turn in the main session... run at a regular interval, which defaults to 30 minutes [1 hour with Anthropic OAuth]... allowing the agent to check in on things." This is OpenClaw's own **gateway-level timer** injecting a fresh turn into an existing session on a clock — nothing to do with pi's `Agent`/`AgentEvent` API, which has no concept of a turn originating from anywhere but an explicit `prompt()` call.
- **Cron jobs**: run in the main session (adding a system event, optionally waking the heartbeat early via `--wake now`/`--wake next-heartbeat`) or in "isolated" fresh sessions. Application-level scheduling and session-spawning, not a pi feature.
- **Background tasks**: described as "the activity ledger that records what detached work happened" across cron/subagent/exec spawns — OpenClaw's own bookkeeping table, analogous in spirit to what `hasPendingBackgroundWork`/`session_crons` do for dilna's idle timer today, but built and owned entirely by OpenClaw.

This confirms the hypothesis from [#97](https://github.com/MrMarble/dilna/issues/97)'s resolution directly: there is no pi-side hook to key a future re-invocation off (no `Stop`-hook equivalent, no `session_crons` push event) because there is no pi-side scheduler at all — OpenClaw's "gateway" layer *is* their equivalent of dilna's `SessionManager`, and they built a real, standalone scheduler there. For dilna, an equivalent would mean `SessionManager` itself owning: a way for the model to register a future wakeup (most naturally another custom tool, since there's no `Stop`-hook signal to intercept — the model would call something like `schedule_wakeup(delayMinutes, note)` and `pi.ts` would need to surface that registration up to `SessionManager` the same way `onInit`/`onRateLimit` callbacks work today), a persisted "next fire time" per session, and a timer/cron loop that re-invokes `runTurn`-equivalent later. This is genuinely new infrastructure comparable in scope to what ADR-0017 already built for the Claude side — not a smaller addition than subagents/background-bash, a larger one.

## 4. Recommendation

**Accept the gap for v1; both the "just write more custom tools" pieces (subagents, background-bash) and the "needs real scheduler infrastructure" piece (cron/`ScheduleWakeup`/heartbeat) are buildable later, on demand, without redesigning anything already decided under this map.** This follows the same bare-minimum-now, revisit-when-actually-needed reasoning already applied to this migration's persistence design (accepting the live-event-aggregation tradeoff for #96 rather than building a sturdier dual-write layer) — none of §2's or §3's pieces are load-bearing for the migration's actual destination (replacing `claude.ts`), and nothing about deferring them forecloses building them later: §2's tools slot into `AgentState.tools` the same way any other tool would, and §3's scheduler is additive to `SessionManager`, not a redesign of it.

Nothing here requires pulling more of `pi-coding-agent`'s product surface (`ExtensionAPI`, `createAgentSession`, `SessionManager`, settings/resource-loader) into dilna than map #93's Notes already scope it to (bare `Agent` + tool factories) — both reference examples use heavier layers than dilna needs, and neither is a "copy this" template for dilna's core embedding. OpenClaw is useful precedent for one thing only: confirming, from a real production system, that this surface is genuinely absent from pi and genuinely requires bespoke host-application infrastructure to get back — which is exactly what this ticket set out to verify.
