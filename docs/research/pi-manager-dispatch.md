# `sessions/manager.ts` dispatch swap: `claude.ts` → `pi.ts`

Design for wayfinder ticket [Design: sessions/manager.ts dispatch swap (claude.ts -> pi.ts)](https://github.com/MrMarble/dilna/issues/97), child of map [#93](https://github.com/MrMarble/dilna/issues/93). Builds directly on [ADR-0020](https://github.com/MrMarble/dilna/blob/adr/0020-adopt-pi-stack/docs/adr/0020-adopt-pi-stack-for-agent-backend.md)'s go decision and the two prior design tickets under this map: [#96](https://github.com/MrMarble/dilna/issues/96) (`docs/research/pi-persistence-bridge.md`, branch `research/pi-persistence-bridge`) for the `AgentEvent`→`Message[]` mapping, and [#95](https://github.com/MrMarble/dilna/issues/95) (`docs/research/pi-tool-confinement.md`, branch `research/pi-tool-confinement`) for the `beforeToolCall` confinement wrapper. Grounded additionally against `pi-agent-core`'s actual `dist/agent.d.ts` (the full `Agent`/`AgentOptions` public surface) and `pi-coding-agent`'s `dist/core/sdk.js` (`createAgentSession`, read for its `new Agent(...)` construction pattern, `streamFn`/`getApiKey` wiring, and tool-factory imports — not for its `SessionManager`/`ModelRuntime`/settings/auth.json layer, which this design does not adopt, per map #93's Notes on staying with the bare `Agent`), installed at 0.84.3 in `/home/atm/Documents/repos/pi-sandbox-spike/node_modules/@earendil-works/`. Cross-referenced against dilna's own `apps/server/src/agents/claude.ts` and `apps/server/src/sessions/manager.ts` line-for-line.

**Purpose:** the concrete diff plan #97 asked for — which `manager.ts` functions change, what `PiHandle` looks like, what gets deleted outright vs. needs a pi-shaped equivalent. Not itself an implementation; precise enough for the execution session map #93 hands off to.

## 0. The structural difference this plan turns on

`ClaudeHandle` exists because `claude-agent-sdk`'s `query()` spawns a **subprocess** and only supports pushing new turns through a hand-rolled async-iterable queue (`createInputQueue`, `claude.ts:987-1025`) — streaming-input mode is a workaround for "one resident subprocess, no per-message respawn" (ADR-0007's "why streaming input"). `pi-agent-core`'s `Agent` is not a subprocess wrapper at all: it's a plain in-process JS object (`new Agent(options)`), and `agent.prompt(text): Promise<void>` resolves when the turn ends — no queue, no subprocess-readiness race, no `createInputQueue`, no `Promise.race([loopPromise, setTimeoutAsync(300)])` spawn-failure probe. A `pi.ts` adapter has nothing subprocess-shaped to wrap; it holds a live `Agent` reference directly. This one difference is what collapses most of `claude.ts`'s plumbing (§2) and simplifies several `manager.ts` paths (§3.4–§3.6) below — it is not one deletion among many, it is the reason several of the others are possible at all.

## 1. `PiHandle`: the `ClaudeHandle` replacement shape

```ts
export type PiHandle = {
  kind: "pi";
  worktreePath: string;
  agent: Agent; // pi-agent-core's Agent instance, held directly — no subprocess, no query object
  listeners: Set<Listener>;
  turnEndListeners: Set<() => void>;
  stop: () => Promise<void>; // agent.abort() + agent.waitForIdle(); no process to kill
  isAlive: () => boolean; // true until stop() is called — no exit-detection needed, see §3.2
  stderrTail: string[]; // kept for shape-parity with the failTurn()/turn_failed detail field, but likely always empty for pi (no subprocess stderr) — provider HTTP errors surface as an errorMessage on AgentState / a turn-failure AgentEvent instead (needs confirming against a live call before assuming this field is dead weight)
};
```

Dropped relative to `ClaudeHandle`, with why:

- `agentSessionId`/`apiKeySource`/`lastAssistantTranscriptUuid` — all three exist to bridge Claude's **external, file-backed transcript**: an opaque id to resume by, an auth-mode readout, and a uuid to gate the transcript-write-lag retry poll on. Per §96, pi has no external transcript at all — dilna's own SQLite rows are the only durable store — so there is nothing these three fields would reference. `agentSessionId`'s *session-linking* role (does `Session.agentSessionId` even mean anything for pi) is `manager.ts`-level, not `PiHandle`-level; see §3.7 and the note to ticket [#99](https://github.com/MrMarble/dilna/issues/99).
- `exitListeners` — exists because a subprocess can die out from under `chatClaude` mid-turn (crash, OOM-kill), and `startClaude`'s `finally` block detects that from the `for await` loop's exit and fires them. An in-process `Agent` object has no analogous "died out from under us" failure mode — a failed provider call surfaces as a rejected `prompt()`/an `agent_end`/error event `chatPi` is already awaiting, not a separate crash channel. If `pi.ts` construction throws or a provider call throws inside `prompt()`, `chatPi`'s own `await agent.prompt(text)` rejects directly — no parallel listener set needed.
- `query`/`sendUserMessage` — replaced by calling `handle.agent.prompt(text)` directly; there is no queue to push onto.

## 2. `claude.ts` deletions vs. pi-shaped equivalents (survey, informs what `pi.ts` needs to expose to `manager.ts`)

Scoped to what determines `manager.ts`'s call surface — not a full `pi.ts` implementation plan (`claude.ts`'s sandbox/writable-paths/mise/pnpm/gh env-var plumbing, `DILNA_AGENT_CONTEXT`, and the `update_repo_memory` MCP tool are `pi.ts`-internal concerns, covered only where they change what `manager.ts` sees).

| `claude.ts` piece | Fate under `pi.ts` |
|---|---|
| `createInputQueue`, the `Promise.race([loopPromise, setTimeoutAsync(300)])` spawn probe | **Deleted outright** — no subprocess, no queue (§0). |
| `NormalizeState` (`toolMessageIds`, `currentTurnMessageId`, `streamedTextApiMessageIds`, `activity`) | **Mostly deleted.** Per #96's own conclusion: pi's events already carry complete messages/tool-call-id-keyed results, so `toolMessageIds`/`currentTurnMessageId`/`streamedTextApiMessageIds` have no pi-side reason to exist. A `Map<toolCallId, messageId>` equivalent is still needed for `tool_call_end`'s `messageId` (`pi.ts`-internal). `activity` (the `turn_activity` aggregate: running tools, Task-tool subagent tracking, thinking-token counts) has no full pi equivalent — see §4, it depends on features pi doesn't have. |
| `normalizeMessage`/`normalizeStreamEvent`/`normalizeAssistantMessage`/`normalizeUserMessage`/`normalizeResultMessage`/`normalizeToolProgress` | **Pi-shaped equivalent required**, mapping `AgentEvent`'s `message_update` deltas (text/thinking) → `token`/`thinking` events and `tool_execution_start`/`tool_execution_end` → `tool_call_start`/`tool_call_end`, mirroring the live half of §96 §1. Structurally simpler than Claude's version — no `stream_event`-vs-complete-message dedup dance (`streamedTextApiMessageIds`), since pi's `message_update` deltas and `message_end`'s complete message aren't both echoing full text the way Claude's `includePartialMessages` does. |
| `normalizeSystemMessage` + its `status`/`api_retry`/`task_*`/`thinking_tokens`/`model_refusal_fallback` branches | **No pi equivalent — deleted, not replaced.** These normalize Claude-CLI-specific system messages (retry backoff, Task-tool subagent lifecycle, refusal-fallback retraction) that don't exist in pi's `AgentEvent` union at all (confirmed: no `status`/`retry`/`task`/`refusal` shape anywhere in `pi-agent-core/dist/types.d.ts`'s `AgentEvent`). See §4 for the Task-tool-subagent piece specifically — it's the one with real feature-loss consequences, not just code deletion. |
| `hasPendingBackgroundWork`, `hooks: { Stop: [...] }`, `ClaudeStartOptions.onPendingWorkChanged` | **No pi equivalent — see §4.** This is the ADR-0017 background-work signal; pi has nothing resembling it. |
| `claudeMessagesToDilna` (manager.ts:147-237) | **Pi-shaped equivalent required**: the turn-slice→`Message[]` merge algorithm §96 §2 already specified in full (walk `agent_end.messages.slice(lengthBefore)`, merge `AssistantMessage`s, fill `tool_call` parts from `ToolResultMessage`s keyed by `toolCallId`). Notably **simpler** than Claude's version: no `origin.kind === "task-notification"` special-casing (pi has no Task-tool concept, §4), no transcript-uuid-keyed id (`Message.id` is synthesized directly, §96 §2 point 4), and — biggest simplification — **no `createdAt` backwards-stamping hack** (`claudeMessagesToDilna`'s `baseCreatedAt - (raw.length - index)` workaround, manager.ts:139-146,167,185): that hack exists purely because Claude's transcript carries no timestamps and is read as an undifferentiated batch after the fact. Pi's `AgentMessage`s (`UserMessage`/`AssistantMessage`/`ToolResultMessage`) all carry a real `timestamp: number` field (§96 §2) — the pi-shaped converter uses that directly, so ordering is authored, not reconstructed. |
| `applyEventToLiveTurn`, `liveTurnReplayEvents` (manager.ts:255-350) | **Unchanged — already backend-agnostic.** Both operate purely on dilna's own `AgentStreamEvent`/`LiveTurn` types, never touching anything Claude-specific. Worth calling out explicitly since it's easy to assume everything in this file needs touching. |
| `fetchClaudeMessagesWithRetry` (manager.ts:1524-1559) | **Deleted outright, no equivalent needed.** This exists solely to poll-and-wait for Claude's transcript file write to catch up with the `result` event (transcript-write lag, `claude.ts`'s own doc comments flag this explicitly). Per §96 §1, pi's `agent_end` event *is* the complete final state, delivered synchronously in the same process — there is no separate file write to lag behind. `persistMessagesFromAgent`'s pi-shaped equivalent reads `agent_end.messages` directly off the event `chatPi`'s own `prompt()` call already awaited. |
| `isSessionResumable`, `buildContextPrimer`, `ActiveAgent.contextPrimer` (manager.ts:1616-1641, 1719-1760, 415, 1159-1161) | **Deleted outright, not replaced with a pi-shaped check.** This whole dance exists because Claude's resume is by opaque id against an external store that can go missing (pod restart wiping `CLAUDE_CONFIG_DIR` before it was fixed onto a persistent volume, per issue #83) — "check resumability first, fall back to a text-recap primer if not" is a *degraded* path for an *unusual* failure. For pi there is no external store to lose: every cold start (first turn ever, or `ensureStarted` re-spawning after an idle-kill/server-restart) does the **same** thing — reconstruct `AgentMessage[]` from dilna's own already-durable SQLite `Message[]` rows (§96 §3's conversion recipe) and pass it as `initialState.messages` to a freshly-constructed `Agent`. There is no "resumable vs. not" branch, no separate primer-text fallback UX, and no `notice` event for "couldn't resume, started fresh primed with history" (manager.ts:1633-1639) — reconstructing from persisted rows *is* the resume path, not a degraded fallback from a better one. This is the single largest simplification in `ensureStarted`/`startAgent`. |
| `resetAllToIdle` → `backfillFromTranscript` (manager.ts:688-746) | **Regresses, does not get a pi-shaped equivalent — flagged as a real consequence, see §4.** Claude's boot-recovery reads from a transcript file that survives independently of dilna's own DB writes (which only happen at turn end); an in-process pi `Agent`'s state has no such independent, durable copy. A dilna server crash mid-turn loses everything the agent did in that turn for a pi-backed session — worse than Claude's current guarantee, not a lateral move. |

## 3. `manager.ts` function-by-function

### 3.1 Imports (top of file)

Delete: `getSessionInfo, getSessionMessages, SDKRateLimitInfo, SessionMessage` from `@anthropic-ai/claude-agent-sdk`; `ClaudeHandle, ClaudeStartOptions, chatClaude, startClaude` from `../agents/claude`. Add: `PiHandle, PiStartOptions, chatPi, startPi` from `../agents/pi` (names chosen to mirror the Claude adapter's exports 1:1, per this repo's "one file per backend, `sessions/manager.ts` dispatches directly" convention — CLAUDE.md's architecture section, ADR-0011).

### 3.2 `ActiveAgent.handle: ClaudeHandle` → `PiHandle`

Straight type swap. Every other `ActiveAgent` field (`idleTimer`, `liveTurn`, `hasPendingBackgroundWork`) is generic already — `contextPrimer` is dropped per §2's row on `buildContextPrimer`. `hasPendingBackgroundWork` stays in the type (harmless if always `false` for pi, see §4) rather than being conditionally typed per backend — one `AgentType`, one adapter, so there's still only one `ActiveAgent` shape to reason about (ADR-0011's standing rule).

### 3.3 `rowToSession`/`toView`/`create`/`delete`/`touch`/`setTitle`/`setStatus`

**Unchanged.** None of these touch the handle or any Claude-specific type — they're already generic over `Session`/`SessionView`. `create()`'s `agentType === "openai"` guard (manager.ts:519) and its `agentType: AgentType = "claude"` default are `AgentType`-value questions, owned by ticket [#99](https://github.com/MrMarble/dilna/issues/99) (schema migration), not this ticket — noted here only so #99 knows this call site exists.

### 3.4 `claudeMessagesToDilna` → its pi-shaped replacement

Per §2's table — new standalone function (name suggestion: `piMessagesToDilna(sessionId, userText, pendingMessage, newEntries)`, taking the turn's raw user text directly rather than round-tripping it through a transcript re-read, per §96 §2 point 5) replaces it in place. `persistConverted` (manager.ts:1452-1504) is **unchanged** — it already operates on `Message[]`, backend-agnostic, exactly as §96 §2 point 5 noted. Its `pending`/`turnUserRow` merge-back logic (manager.ts:1483-1498) simplifies for pi callers specifically because the new converter is handed the pending placeholder directly rather than needing to find-and-patch it after the fact — worth a follow-up look during implementation, but `persistConverted` itself needs no signature change to support that.

### 3.5 `backfillFromTranscript`/`resetAllToIdle`

`backfillFromTranscript` (manager.ts:726-746) is Claude-specific (`getSessionMessages` against `session.agentSessionId`). For a `session.agentType === "pi"` row, **there is nothing to backfill from** (§2, §4) — `resetAllToIdle`'s loop (manager.ts:688-717) needs an `agentType` branch: Claude rows keep calling `backfillFromTranscript`; pi rows skip straight to `promotePendingUserMessage` (the "transcript didn't capture the user's message" path always taken, since there's no transcript to check) and the status reset. No pi-side data recovery happens — this is the regression flagged in §2/§4, not something this function can paper over.

### 3.6 `ensureStarted`/`startAgent`

The resumability/primer logic (manager.ts:1615-1641) is deleted per §2. `startAgent`'s pi-shaped body:

1. Read the session's persisted `Message[]` via the existing `getMessages(id)` (manager.ts:965-980, already generic, unchanged).
2. Convert to `AgentMessage[]` via §96 §3's recipe (a `pi.ts`-exported helper, name suggestion `dilnaMessagesToInitialState`).
3. `const handle = await startPi({ worktreePath: session.worktreePath, initialMessages, onEvent-wiring-equivalent-of-onInit/onRateLimit-if-any (see §4's rate-limit note), ... })`, where `startPi` constructs `new Agent({ initialState: { messages: initialMessages, model, tools, systemPrompt }, streamFn, getApiKey, beforeToolCall: <the #95 wrapper>, ... })` internally (`pi.ts`-internal — model/provider/`getApiKey` sourcing is ticket [#98](https://github.com/MrMarble/dilna/issues/98)'s scope, not this one's).
4. No `resumeId`/`isSessionResumable` branch, no `notice` for "couldn't resume" (§2) — every start looks like this, including the very first turn of a session (where `initialMessages` is simply empty).

`onInit`'s role (persisting `agentSessionId` the moment it's known, ADR-0014's "don't orphan an interrupted first turn") has no pi analogue to persist *early* — see §3.7, pi's `agentSessionId`-equivalent (if `Session` keeps one at all, per #99) is either not meaningful the same way or is known upfront rather than arriving mid-handshake, since pi never has an `init`-message handshake to wait for (no subprocess to spawn, §0).

### 3.7 `Session.agentSessionId`'s role, flagged for ticket #99

Throughout `manager.ts`, `agentSessionId` currently does three jobs: (a) the resume key (§2: gone for pi), (b) the `getSessionMessages`/`getSessionInfo` lookup key for reading Claude's transcript (§2: gone, pi has no such external store), (c) title auto-sync input (`maybeSyncTitle`, manager.ts:1897-1912, calls `getSessionInfo` for `info.summary`). None of the three survive as-is for pi. This ticket doesn't decide what (if anything) replaces the column — flagging it concretely for #99 rather than deciding it here, since #99 owns the schema. Two live options worth that ticket's attention: drop the column entirely (nothing left that needs it), or repurpose it to store `Agent.sessionId` (the opaque provider cache-affinity token, `AgentOptions.sessionId`, `pi-agent-core/dist/agent.d.ts` — a different concept from what the column means today, forwarded to the provider for cache-aware backends, not a resume/lookup key).

### 3.8 `maybeSyncTitle`

Depends on `getSessionInfo` (Claude-transcript-backed). No pi equivalent exists for "the CLI auto-derived a session title" — pi's `Agent`/`AgentEvent` has no title/summary concept at all. **Deleted, not replaced**, unless a future `pi.ts` wants to derive a title itself (e.g. a cheap follow-up prompt asking the model to summarize) — out of scope for this ticket to decide; flagged as a UX regression (every session keeps its generic `Session <id>` placeholder title indefinitely) worth the map's attention if it matters enough to fix, not silently absorbed as "equivalent."

### 3.9 `runTurn`, `chatClaude` → `chatPi`

`runTurn`'s overall shape (claim → ensureStarted → transitionStatus("working") → race the chat call against `TURN_TIMEOUT_MS` → persist → status transition) is unchanged structurally. `chatPi(handle, opts)` replaces `chatClaude`: subscribes to `handle.agent` via `agent.subscribe(listener)` (`pi-agent-core/dist/agent.d.ts`'s documented API) instead of `handle.listeners`/`turnEndListeners`, normalizes each `AgentEvent` to `AgentStreamEvent` via §2's pi-shaped normalizer, and resolves when `agent.prompt(text)`'s promise resolves (no separate `turnEndListeners` handshake — `prompt()` itself is the completion signal, §0). The `crashed`/`!handle.isAlive()` branch (manager.ts:1180-1187) has no real pi equivalent per §1's `PiHandle.isAlive` note — a failed `prompt()` call surfaces as a normal rejection from the `await`, indistinguishable in kind from Claude's `TurnTimeoutError` path except it doesn't need the separate exit-listener race to detect it.

## 4. New fog surfaced by this ticket, not decided here

Two things fell out of tracing every `claude.ts`-specific `manager.ts` code path that neither ADR-0020 nor tickets #95/#96 addressed, and that this ticket's scope (the dispatch mechanics) isn't the right place to resolve:

1. **ADR-0017's background-work-aware idle timer, the Task-tool subagent feature, and `ScheduleWakeup`/`CronCreate`/`/loop` session-cron registrations have no `pi-agent-core`/`pi-coding-agent` equivalent at all** — confirmed by an exhaustive grep across both packages' installed `dist/` trees for anything background-task/subagent/cron-shaped: zero matches. These aren't `claude.ts` implementation details; they're capabilities of the Claude Code CLI product itself that `claude-agent-sdk` exposes signals for. `pi-agent-core`'s bare `Agent` is a single synchronous tool-calling loop with no concept of backgrounding work or scheduling a future prompt injection. **This means a session running on `pi.ts` cannot register a background shell job, spawn a Task-tool subagent, or use `ScheduleWakeup`/`CronCreate`/`/loop` the way a `claude.ts`-backed session can today** — not a missing normalizer to write, a missing capability in the backend itself. Whether that's an acceptable loss (map #93's Notes don't mention it) or a blocker that needs its own resolution before this migration can actually replace `claude.ts` needs a decision the map hasn't made yet.
2. **`resetAllToIdle`'s crash-recovery guarantee (ADR-0014) regresses for pi-backed sessions** (§2, §3.5): a dilna server crash mid-turn loses everything the agent produced in that turn, where a Claude-backed session recovers it from the independent transcript file. Whether that's acceptable given map #93's "bare-minimum persistence" framing, or worth an incremental-persistence design (e.g. persisting on every `message_end`, not just at `agent_end`) needs its own decision.

Both are added to map #93's **Not yet specified** rather than resolved in this ticket, since neither is "the dispatch mechanics" this ticket was scoped to answer, and both need their own judgment call about acceptable scope, not a code sketch.

## 5. Summary for the execution session

Net line-count direction: `manager.ts` gets **smaller**, not larger — the resumability/primer dance, the transcript-retry poll, and the Claude-specific transcript-recovery path all disappear with no pi-shaped replacement needed, while the one genuinely new piece (`piMessagesToDilna`) is simpler than what it replaces (§2, §3.4). The `PiHandle` surface `pi.ts` needs to expose to `manager.ts` is smaller than `ClaudeHandle`'s (§1). The two items in §4 are the ones this ticket cannot wave through as "just a different normalizer" — they're capability gaps the map needs to explicitly accept or address before execution.
