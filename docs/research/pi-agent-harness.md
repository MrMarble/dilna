# pi-agent-core message model + pi-coding-agent read/edit/write confinement/resume

Research for Wayfinder ticket [Research: pi-agent-core message model + pi-coding-agent read/edit/write confinement/resume](https://github.com/MrMarble/dilna/issues/90) (child of the "Map: replace claude-agent-sdk with a provider-agnostic agent harness (pi stack + sandbox-runtime)" map, #87). Grounded by installing the real, currently-published packages into a scratch directory outside this repo (`npm install @earendil-works/pi-ai@0.84.2 @earendil-works/pi-agent-core@0.84.2 @earendil-works/pi-coding-agent@0.84.2`, npm registry, 2026-08-21) and reading their actual `.d.ts` declarations and bundled `.js` source under `node_modules/@earendil-works/*/dist/` — the same method as `claude-agent-sdk-in-turn-signals.md`: the installed package is ground truth, not the pi GitHub repo's docs or README. All three packages exist, are public, and installed cleanly at version **0.84.2** (`@earendil-works/pi-ai`, `@earendil-works/pi-agent-core`, `@earendil-works/pi-coding-agent`) with no auth needed.

**Purpose:** establish ground-truth facts for ADR ticket #92 (not written here) to decide against. This doc enumerates and classifies what the installed packages actually do; it makes no go/no-go recommendation.

## 0. Package shapes at a glance

- `@earendil-works/pi-ai` — multi-provider LLM client. Defines the wire-level `Message` union (`UserMessage | AssistantMessage | ToolResultMessage`, `pi-ai/dist/types.d.ts:292-335`) that everything downstream is built on. Tool calls and tool results are **separate message roles** (`AssistantMessage.content` holds `ToolCall` blocks; the result is a distinct `role: "toolResult"` message keyed by `toolCallId`) — structurally the same split Claude's own SDK uses (`tool_use` block + a later synthetic `tool_result` user message), which is exactly what `claude.ts`'s `toolMessageIds` map exists to re-merge into dilna's single `MessagePart.tool_call { input, output }` shape.
- `@earendil-works/pi-agent-core` — ships **two independent things** under one package, not one coherent "agent + persistence" system:
  1. `Agent` (`dist/agent.d.ts`) — the bare, in-memory, event-driven tool-calling loop.
  2. `harness/*` — a separate, more ambitious "durable session" subsystem (`Session`, `JsonlSessionRepo`, `AgentHarness`) that is **only partially implemented** (§1.2).
- `@earendil-works/pi-coding-agent` — the actual `pi` CLI product. It does **not** use `pi-agent-core`'s `harness/*` subsystem at all for its own persistence; it wraps the bare `Agent` directly and rolls its own JSONL session store (`core/session-manager.ts`) and orchestration class (`core/agent-session.ts`). Its `core/sdk.ts` (`createAgentSession`) is the documented embedding entry point and is where the real resume/persistence wiring lives (§1.3, §3).

## 1. Message persistence

### 1.1 The bare `Agent` class: in-memory only

`pi-agent-core/dist/agent.d.ts` defines `Agent` as a stateful wrapper with `_state`, a `listeners` set, and `steeringQueue`/`followUpQueue` arrays — no filesystem I/O anywhere in the class. `AgentState.messages` (`dist/types.d.ts:299-301`) is a plain in-memory accessor: `set messages(messages: AgentMessage[])` / `get messages()`, documented as copying the assigned array. `AgentOptions` (`dist/agent.d.ts:5-25`) has no `session`, `persist`, `transcriptPath`, or similar field. Everything the `Agent` emits is via `AgentEvent` (`dist/types.d.ts:374-412`): `agent_start` / `agent_end` / `turn_start` / `turn_end` / `message_start` / `message_update` / `message_end` / `tool_execution_start` / `tool_execution_update` / `tool_execution_end` — a pure in-process event stream, structurally analogous to dilna's own `AgentStreamEvent` but with no disk-backed counterpart the way Claude's CLI transcript is. If a caller only imports `Agent`, there is **no on-disk transcript equivalent to `getSessionMessages`** — persistence is entirely the caller's problem, which is exactly the "aggregate the event stream into dilna's own shapes yourself" path ADR-0006 rejected for both prior backends.

### 1.2 `harness/session/*`: a real on-disk store, wired to an unfinished orchestrator

`pi-agent-core` also exports (via `dist/index.d.ts:12` re-exporting `./harness/session/index.ts`) a second, unrelated persistence layer:

- `JsonlSessionRepo` (`dist/harness/session/jsonl/repo.js`) is a fully implemented, real JSONL-backed session store: `create()`/`open()`/`list()`/`fork()`/`delete()` against append-only `.jsonl` files under a caller-supplied `sessionsRoot`, one directory per encoded cwd (`jsonlSessionDirectoryName`), files named `<ISO-timestamp>_<sessionId>.jsonl`. `Session` (`dist/harness/session/session.d.ts`) is a git-like tree structure over that store: `Entry` types include `MessageEntry { type: "message", message: AgentMessage, parentId, seq }` alongside `ModelChangeEntry`, `CompactionEntry`, `BranchSummaryEntry`, `CustomEntry` (`dist/harness/session/types.d.ts:12-58`), plus a separate `LaneRecord` log (`OperationStartedRecord`, `ToolStartedRecord`, `UsageRecord`, etc., same file, lines 59-179) for crash-recoverable operation bookkeeping. This part of the stack is real and exercised — `pi-coding-agent`'s CHANGELOG (`node_modules/@earendil-works/pi-coding-agent/CHANGELOG.md:200`) confirms: *"Added inherited v4 `JsonlSessionRepo` support for append-only JSONL harness sessions"*.
- **But the class meant to drive it — `AgentHarness` (`dist/harness/agent-harness.d.ts`/`.js`) — is a stub.** Reading `agent-harness.js` directly: every state-mutating method that would actually run a turn or resume one — `prompt()`, `skill()`, `promptFromTemplate()`, `compact()`, `navigateTree()`, `resume()`, `abort()`, `steer()`, `followUp()`, `nextRun()`, `cancelQueued()`, `recordUsage()`, `waitForIdle()`, `runWhenIdle()`, `peekAction()`, `executeAction()`, `runToCompletion()`, `watch()`, `lane()`, `createLane()`, `lanes()`, `watchSession()` — is implemented as `return this.unavailable("<name>")`, which rejects with `new HarnessNotImplemented(operation)` (`Error: "AgentHarness.<operation> is not implemented yet"`, `dist/harness/agent-harness.js:44-51,109-111`). Only trivial getters/setters work (`model`, `thinkingLevel`, `tools`, `resources`, `streamOptions`, `retryPolicy`, `compactionSettings`, `steeringMode`/`followUpMode`). `AgentHarness.create()` itself throws `HarnessNotImplemented("create.restore")` the moment it finds *any* existing record in the passed `Session` (`dist/harness/agent-harness.js:103-107`) — i.e. it cannot even restore a previously-used session, only construct a brand-new empty one.
- This is confirmed as the current, acknowledged state (not a bug found by accident) by `pi-coding-agent`'s own CHANGELOG: *"Added the inherited compile-complete `AgentHarness` v2 scaffold; unfinished operation paths reject with `HarnessNotImplemented` while durable execution is implemented"* (`CHANGELOG.md:202`), and *"Promoted the inherited v2 session and `AgentHarness` API from pi-agent-core's experimental entrypoint to its default export"* (`CHANGELOG.md:169-170`) — i.e. it was recently promoted out of an "experimental" subpath while still not functionally complete.

**Net for §1.2: the storage primitives (`JsonlSessionRepo`/`Session`/`SessionStorage`) are real and on-disk; the orchestrator meant to connect them to a running `Agent` (`AgentHarness`) is scaffolding that rejects on every operation that would matter for a chat backend.** A caller could in principle drive `Session`/`JsonlSessionRepo` directly (append `MessageEntry`s itself, bypass `AgentHarness` entirely) — but that is then equivalent to hand-rolling persistence again, just against a lower-level, purpose-built format instead of a bare event stream.

### 1.3 What `pi-coding-agent` (the actual product) does instead

`pi-coding-agent` does not use `harness/*` for its own persistence at all. Its `core/session-manager.ts` `SessionManager` class (`dist/core/session-manager.d.ts`) is a separate, independently-implemented JSONL transcript store:

- Real file writes, confirmed in `dist/core/session-manager.js`: `writeFileSync`/`appendFileSync` of `` `${JSON.stringify(entry)}\n` `` — genuine JSONL, one file per session at `~/.pi/agent/sessions/<encoded-cwd>/<ISO-timestamp>_<sessionId>.jsonl` by default (`getDefaultSessionDir`, `config.ts:412-417` resolves the root to `~/.pi/agent` via `CONFIG_DIR_NAME` from `package.json`'s `piConfig.configDir`, default `.pi`).
- `SessionManager.appendMessage(message: Message | CustomMessage | BashExecutionMessage)` (`dist/core/session-manager.d.ts:217`) writes one `SessionMessageEntry { type: "message", id, parentId, timestamp, message }` per call — i.e. **one entry per whole message, not per token/event** — the same "aggregate on write" shape ADR-0006 chose for dilna's own `Message`/`MessagePart`, and the same granularity Claude's own transcript uses.
- `AgentSession` (`core/agent-session.ts`, wraps a `pi-agent-core` `Agent` instance directly per its `AgentSessionConfig.agent: Agent` field) ties the two together: its class doc comment states plainly *"Session persistence is handled internally (saves messages on `message_end`)"* (`dist/core/agent-session.d.ts:1-14,273-276`) — i.e. `AgentSession` subscribes to the bare `Agent`'s in-memory `AgentEvent` stream and calls `sessionManager.appendMessage(...)` itself on `message_end`. This confirms the answer to the framing question directly: **there is no built-in bridge inside `pi-agent-core` from `Agent`'s event stream to disk — `pi-coding-agent` builds that bridge itself**, in application code, which is exactly the "aggregate the event stream into your own persisted shape" approach ADR-0006 rejected for dilna's own adapters. `pi-coding-agent` just happens to already have done that work for its own `SessionEntry` format; a dilna adapter built on the bare `Agent` would have to write the equivalent of `AgentSession`'s `message_end` handler itself, or pull in the whole of `pi-coding-agent` (CLI, TUI, extensions, and all) to get it for free.

## 2. Read/Edit/Write path confinement

Read the actual `execute()` implementations, not just the exported type signatures, for `createReadTool`/`createEditTool`/`createWriteTool` from `@earendil-works/pi-coding-agent` (`core/sdk.ts`, re-exporting `core/tools/{read,write,edit}.ts`):

- **`createReadTool`/`createReadToolDefinition`** (`dist/core/tools/read.js:135-163`): resolves the model-supplied `path` via `resolveReadPathAsync(path, cwd)` → `resolveToCwd(filePath, cwd)` (`dist/core/tools/path-utils.js:42-44`) → `resolvePath(filePath, cwd, { normalizeUnicodeSpaces: true, stripAtPrefix: true })` (`dist/utils/paths.js:82-86`). That function does exactly: normalize (tilde/unicode-space handling), then `isAbsolute(normalized) ? nodeResolvePath(normalized) : nodeResolvePath(cwd, normalized)`. **No check anywhere that the resolved path is inside `cwd`.** An absolute path, or a relative path containing `../../../etc/passwd`, resolves and is read exactly the same as a path inside the worktree.
- **`createWriteTool`** (`dist/core/tools/write.js:136-169`): `const absolutePath = resolveToCwd(path, cwd)`, then `ops.mkdir(dirname(absolutePath))` and `ops.writeFile(absolutePath, content)` — same unguarded resolution, no boundary check before the write.
- **`createEditTool`** (`dist/core/tools/edit.js:168-227`): `const absolutePath = resolveToCwd(path, cwd)`, then reads/mutates that path directly — same pattern again.
- `utils/paths.js` does define `getCwdRelativePath(filePath, cwd)` (lines 87-94), which *does* compute whether a path is inside `cwd` (`isInsideCwd`) — but grep across the whole installed `pi-coding-agent/dist` tree shows its only callers are `formatPathRelativeToCwdOrAbsolute` (display formatting for the TUI's path breadcrumbs) and the interactive-mode tree/file selector UI (`modes/interactive/components/tree-selector.js`, `interactive-mode.js`). It is never called from any tool's `execute()` path. The confinement *primitive* exists in the codebase; it is not wired into the tools.
- `createAgentSession`'s `CreateAgentSessionOptions` (`dist/core/sdk.d.ts:10-56`) has no `allowedPaths`, `confineTo`, `jailCwd`, or similar option — nothing at the SDK-embedding layer offers to turn this on either.

**This is confirmed as deliberate, stated product design, not an oversight**, by the bundled `docs/security.md` (`node_modules/@earendil-works/pi-coding-agent/docs/security.md`, shipped with the installed package): *"Pi does not include a built-in sandbox. Built-in tools can read files, write files, edit files, and run shell commands with the permissions of the pi process... This is intentional... Real isolation needs to come from the operating system or a virtualization/container boundary."* This is the same conclusion dilna's own ADR-0010 reached about Claude Agent SDK's Read/Edit/Write tools ("governed by Claude's own permission system, which dilna bypasses entirely") — except pi states it as the permanent design rather than a gap to eventually close with an SDK-level flag.

**One historical wrinkle worth flagging rather than silently smoothing over:** `pi-coding-agent`'s own `CHANGELOG.md` has a single, much older entry (`v0.11.7`, 2025-12-01, `CHANGELOG.md:5342`) reading *"Fix read path traversal vulnerability. Paths are now validated to prevent reading outside the working directory or its parents... Symlinks are resolved before validation."* That claim does not match the current (`v0.84.2`) `read.js` source above — no such validation exists in the code actually shipped today, and nothing in the intervening ~73 versions of changelog mentions removing or superseding it. Either that fix lived in code later refactored away without a changelog note, or it was superseded by the current `docs/security.md` stance (no in-tool confinement at all, push isolation to the OS/container layer) without the changelog calling out the reversal explicitly. Not resolved further here — noted as exactly the kind of discrepancy that would need live verification (run the actual installed `read` tool against a `../` path and confirm it reads through) before an ADR relies on either claim.

**A secondary, narrower observation:** `@earendil-works/pi-agent-core` itself also ships a *second*, independent read/write/edit tool implementation under `harness/tools/*` (`dist/harness/tools/read.js`, separate from `pi-coding-agent`'s). It resolves paths via a caller-injected `env: ExecutionEnv`'s `absolutePath()`/`readBinaryFile()` methods (`dist/harness/tools/path-utils.js:8-10`) rather than calling Node's `fs`/`path` directly. Same result today — no confinement logic in the default implementation shown here — but the indirection through an injectable `ExecutionEnv`/`FileSystem` interface (`dist/harness/types.ts`, exported as `FileSystem`/`ExecutionEnv` from the package root) is a structurally different extension point: a caller supplying their own `ExecutionEnv.absolutePath` could enforce confinement there. This is irrelevant if dilna adopts `pi-coding-agent`'s tools (as the map issue names) but is a fact about the sibling package worth having on record.

## 3. Session resume

### 3.1 The bare `Agent`: no resume API at all

`pi-agent-core`'s `Agent` class (`dist/agent.d.ts`) has no `resume`, `restore`, `load`, or `fromTranscript` method or static factory. The only way prior state enters an `Agent` is `AgentOptions.initialState?.messages` at construction time, or reassigning `agent.state.messages = [...]` after construction (both are the same in-memory array-copy, per `AgentState.messages`'s doc comment). There is no session-id concept in `Agent` at all beyond `AgentOptions.sessionId?: string` (`dist/agent.d.ts:20`, `dist/types.d.ts`), which the class doc marks *"Session identifier **forwarded to providers** for cache-aware backends"* — i.e. it's an opaque cache-affinity token passed to the LLM provider's API, not a handle pi itself uses to look anything up.

### 3.2 `AgentHarness.resume()`: present in the type, throws in the implementation

The richer `harness/*` layer does define a `resume(): Promise<ResumeResult>` method on both the `AgentLane` interface and the concrete `AgentHarness` class (`dist/harness/agent-harness.d.ts:356,415`), with `ResumeResult`/`ResumeOutcome`/`ResumeRejected` types describing what a real resume would report (`SuspendedOperation`, `NothingToResume`, `MissingIdentities`, etc. — a genuinely well-designed shape for reporting "here's what a crash-recovered resume actually found"). As established in §1.2, the actual method body is `return this.unavailable("resume")`, i.e. it unconditionally rejects with `HarnessNotImplemented("resume")` today. **The documented resume API exists only in the type declarations; it is non-functional in the shipped 0.84.2 build.**

### 3.3 What actually resumes a conversation today: `pi-coding-agent`'s manual replay

Reading `createAgentSession` in `dist/core/sdk.js` (lines 66-267) end to end shows the real, working mechanism, and it is exactly the "replay stored messages into a new `Agent` instance manually" pattern the ticket asked about verifying:

1. `const sessionManager = options.sessionManager ?? SessionManager.create(cwd, ...)` — resolve which session-store instance to use. `SessionManager.create()` (`session-manager.js:1176-1179`) **always creates a brand-new session file**; it does not auto-detect or resume an existing one for the cwd.
2. Actual resume requires the caller to pass a specific `sessionManager` explicitly, via one of two static factories on `SessionManager` (`dist/core/session-manager.d.ts:318-325`, confirmed against `.js:1186-1221`):
   - `SessionManager.open(path, sessionDir?, cwdOverride?)` — open one specific session file by path (reads the file's own header for the `cwd` it was created against unless overridden).
   - `SessionManager.continueRecent(cwd, sessionDir?)` — find the most recently modified `.jsonl` file for a given cwd (`findMostRecentSession`) and open that.
   - Both are file/path-keyed, not opaque-id-keyed the way `resume: session.agentSessionId` is for Claude — there is no `SessionManager.openById(id)`; a caller wanting id-based resume has to track the file path itself (or scan `SessionManager`'s own listing, which is also path-based).
3. `const existingSession = sessionManager.buildSessionContext()` (`sdk.js:81`) — reads the JSONL file end-to-end via `buildSessionContext(entries, leafId, byId)` (`session-manager.js:232`, walks the parent-linked entry tree from the leaf) and resolves it into `{ messages: AgentMessage[], thinkingLevel, model }`.
4. A brand-new `Agent` is constructed unconditionally (`sdk.js:170-231`) — there is no "resume mode" constructor path, no `resume:` option passed anywhere near `new Agent(...)`.
5. **The actual resume step is one direct assignment**: `if (hasExistingSession) { agent.state.messages = existingSession.messages; ... }` (`sdk.js:232-238`). That's it — the new `Agent`'s in-memory transcript is set by hand from what `SessionManager` read off disk. Model and thinking-level are separately restored from dedicated entry types (`ModelChangeEntry`/`ThinkingLevelChangeEntry`) with their own fallback logic (`sdk.js:84-131`), not bundled into the message replay itself.
6. Every later `AgentSession.subscribe()`-driven `message_end` continues to call `sessionManager.appendMessage(...)` (per §1.3) — so the file the next resume reads from is the same one being continuously appended to, not a separate write-back step.

**One documentation/type mismatch worth flagging as-is rather than resolving:** `core/sdk.d.ts`'s own JSDoc example for `createAgentSession` shows `// Continue previous session\nconst { session, modelFallbackMessage } = await createAgentSession({ continueSession: true });` (`dist/core/sdk.d.ts:46-49`, verbatim in `dist/core/sdk.js:46-49` too) — but `CreateAgentSessionOptions` (the actual parameter type, same file, lines 10-56) has **no `continueSession` field at all**. Passing `{ continueSession: true }` today would silently do nothing (excess property, not type-checked at the call site if not object-literal-inferred, and even where it is, it's just ignored at runtime by `createAgentSession`'s destructuring) — the function would still create a fresh, empty session per point 1 above, since `options.sessionManager` was never actually supplied. The real resume path is `sessionManager: SessionManager.open(path)` or `SessionManager.continueRecent(cwd)`, not a boolean flag. This is exactly the class of claim ADR-0007's method flags as needing live verification rather than trusting a doc comment — confirmed here by reading the type declaration next to the doc comment, not yet by actually running it.

### 3.4 What would need live verification (not resolved by reading types/source alone)

Analogous to how `resume: session.agentSessionId` needed to be run against a real Claude subprocess before ADR-0007 could rely on it, the following are clear from the installed `.d.ts`/`.js` but not yet exercised end-to-end:

- Whether `agent.state.messages = existingSession.messages` round-trips cleanly through a real provider call — e.g. whether `AssistantMessage.deferred`/`DeferredHandle` (pending async tool-use state, `pi-ai/dist/types.d.ts:281-291,308`) or in-flight `ToolResultMessage`s left mid-turn by a killed process replay correctly into a fresh `Agent`, or whether resuming mid-turn work requires the caller to also reconstruct the low-level agent-loop's turn state (nothing in `sdk.js`'s restore path does anything special for an interrupted last message — it just takes whatever `buildSessionContext` returns).
- Whether `SessionManager.continueRecent`'s "most recent `.jsonl` for this cwd" resolution is safe for dilna's model of "one session id ↔ one worktree, looked up explicitly by dilna's own DB row" rather than "most recently touched file in a directory" — dilna would almost certainly use `SessionManager.open(exactPath)` instead, but that requires dilna to persist the `.jsonl` file's path itself (there is no shorter opaque-id form to store, unlike Claude's `session_id` string).
- Whether `HarnessNotImplemented`'s `resume()` stub is scheduled to land soon (the CHANGELOG framing — "compile-complete scaffold... while durable execution is implemented" — reads as active, incremental work, not an abandoned direction) — worth a fresh `npm view` check at ADR time rather than assuming 0.84.2's gap persists.

## 4. Summary

| Question | Finding |
|---|---|
| On-disk transcript equivalent to Claude's `getSessionMessages`? | Not from the bare `pi-agent-core` `Agent` (in-memory only). `pi-agent-core`'s own `harness/session/*` JSONL store (`JsonlSessionRepo`) is real, but its orchestrator (`AgentHarness`) rejects every operation that would use it for a live conversation (`HarnessNotImplemented`). `pi-coding-agent` has a real, working, per-message JSONL transcript (`SessionManager`) — but it's `pi-coding-agent`'s own bespoke code wrapping the bare `Agent`'s event stream, not something `pi-agent-core` provides out of the box. |
| Does `createReadTool`/`createEditTool`/`createWriteTool` enforce worktree confinement? | No. All three resolve `path` against `cwd` with no boundary check (verified in `read.js`/`write.js`/`edit.js` source); confirmed as pi's stated permanent design in its bundled `docs/security.md` ("no built-in sandbox... intentional"), not merely an omission. A `getCwdRelativePath`/`isInsideCwd` primitive exists in `utils/paths.js` but is only used for TUI display, never wired into a tool's `execute()`. |
| Documented resume API in `pi-agent-core`? | `AgentHarness.resume()` exists in the type declarations but throws `HarnessNotImplemented` in the shipped 0.84.2 build. The bare `Agent` class has no resume API of any kind. The actually-working resume path lives in `pi-coding-agent` (`createAgentSession` + `SessionManager.open`/`continueRecent`), and is a manual replay: read the JSONL transcript off disk, construct a brand-new `Agent`, and assign `agent.state.messages` directly — exactly the "replay stored messages into a new `Agent` instance manually" alternative the ticket asked about verifying. |
