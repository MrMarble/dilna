# Reject the pi stack as a provider-agnostic replacement for claude-agent-sdk

## Context

`apps/server/src/agents/claude.ts` depends on `@anthropic-ai/claude-agent-sdk`, which wraps Claude Code's own CLI/SDK. Three closed incidents — [#70](https://github.com/MrMarble/dilna/issues/70), [#74](https://github.com/MrMarble/dilna/issues/74), [#83](https://github.com/MrMarble/dilna/issues/83) — all traced back to the same shape of friction living inside that dependency: `$HOME`-rooted toolchain state getting wiped between Bash tool calls, writable-path grants that were inert until the host directory already existed, and the `dangerouslyDisableSandbox` escape hatch (ADR-0010's Follow-ups 1, 3, 4). Separately, dilna's GA plan wants broader provider support (DeepSeek and others), which `claude-agent-sdk` — an Anthropic-specific SDK — can't give us.

Those two pressures motivated evaluating a provider-agnostic stack: `@earendil-works/pi-ai` (multi-provider LLM client, including Anthropic subscription/OAuth auth) + `@earendil-works/pi-agent-core` (tool-calling loop) + `@earendil-works/pi-coding-agent`'s tool factories (bash/read/edit/write/grep/find/ls) + `@anthropic-ai/sandbox-runtime` (the same sandbox engine already used inside `claude-agent-sdk`), wired through pi's `BashOperations` hook — tracked as wayfinder map [#87](https://github.com/MrMarble/dilna/issues/87). This ADR is that map's destination ticket ([#92](https://github.com/MrMarble/dilna/issues/92)), closing the map with a **no-go**.

A fully generic "any token/endpoint" client, and opencode itself, were both ruled out before this evaluation started (opencode was already tried wrapped in bwrap and hit the same nested-spawn-under-external-sandbox failure ADR-0010 documents, plus API-key-only auth — see #87's Notes). The pi stack was the only candidate that looked viable enough to actually spike.

## Decision

**Keep `@anthropic-ai/claude-agent-sdk` as dilna's only agent backend.** No `pi.ts` adapter gets built. `apps/server/src/agents/claude.ts` is unchanged by this ADR.

Two child tickets under map #87 verified the candidate stack against the real, installed packages (`@earendil-works/pi-ai`/`pi-agent-core`/`pi-coding-agent` v0.84.2, `@anthropic-ai/sandbox-runtime` v0.0.73) rather than trusting docs or the pi GitHub repo, and all three of the stack's supposed advantages failed to hold:

**1. Anthropic support regresses, not just stays flat.** [Prototype #91](https://github.com/MrMarble/dilna/issues/91) verified `/login` in the pi CLI live: the PKCE flow, browser login, and token exchange all complete against a real Anthropic account. But `pi-ai`'s Anthropic OAuth registers its own third-party `client_id` (`9d1c250a-e61b-44d9-88ed-5944d1962f5e`, decoded from the base64 literal in `pi-ai/dist/auth/oauth/anthropic.js`), distinct from Claude Code's own official client. Anthropic bills all usage through it as per-token "extra usage" (the overage pool at `claude.ai/settings/usage`), never against the Claude Pro/Max plan's included quota — stated plainly in `pi-coding-agent`'s own `docs/providers.md`: *"Third-party harness usage draws from extra usage and is billed per token, not against Claude plan limits."* There is no config to change this: no client_id override exists, and the `warnings.anthropicExtraUsage` setting (`docs/settings.md`) only toggles whether pi *warns* about it. `claude-agent-sdk` avoids this entirely because it wraps Claude Code's own first-party OAuth session, which draws from the plan's included quota — confirmed by the map's own driver hitting this exact warning live and rejecting it for his own usage.

**2. Filesystem safety regresses.** [Research #90](https://github.com/MrMarble/dilna/issues/90) found, and [Prototype #91](https://github.com/MrMarble/dilna/issues/91) proved live, that `pi-coding-agent`'s `read`/`edit`/`write` tools have zero worktree confinement: `resolveToCwd()` (`core/tools/path-utils.js`) resolves a path against `cwd` with no containment check, and this is stated as *permanent, intentional* design in pi's own bundled `docs/security.md` ("Pi does not include a built-in sandbox... this is intentional... real isolation needs to come from the operating system or a virtualization/container boundary"), not a gap pi intends to close. A `getCwdRelativePath`/`isInsideCwd` primitive exists in `utils/paths.js` but is only wired into TUI breadcrumb display, never into any tool's `execute()`. The candidate stack's `sandbox-runtime` piece only covers this by wrapping the *Bash* tool's shell string (via pi's `BashOperations` hook) — the live spike confirmed a Bash command targeting a path outside the scratch worktree correctly failed ("Read-only file system"), but the same sandbox left the `write` tool completely unguarded: both an absolute-path write and a relative `../` write to outside the worktree **succeeded**, proof that `sandbox-runtime` wired this way never touches the process's other file-mutating tools at all. This is a strictly worse position than what dilna already has: ADR-0010 accepted that Claude's own Read/Edit/Write tools aren't OS-sandboxed either, but they're at least gated by Claude's own permission system (which dilna currently bypasses via `bypassPermissions`, per ADR-0003) — pi's tools have no equivalent gate to bypass; there's simply nothing there.

**3. Persistence and resume aren't free.** [Research #90](https://github.com/MrMarble/dilna/issues/90) (full findings: [`docs/research/pi-agent-harness.md`](https://github.com/MrMarble/dilna/blob/research/pi-agent-harness/docs/research/pi-agent-harness.md) on branch `research/pi-agent-harness`, unmerged) found that `pi-agent-core`'s bare `Agent` class is in-memory only — no transcript, no resume API beyond an opaque provider-cache token. `pi-agent-core` does ship a `harness/*` "durable session" subsystem (`Session`/`JsonlSessionRepo`, a real, working JSONL store) but its orchestrator, `AgentHarness`, rejects every state-mutating operation (`prompt()`, `resume()`, `compact()`, etc.) with `HarnessNotImplemented` — confirmed as a stub in the shipped 0.84.2 build (`pi-coding-agent`'s own CHANGELOG calls it a "compile-complete scaffold" with "unfinished operation paths"), not something we mis-configured. The only working persistence/resume path belongs to `pi-coding-agent` itself: its `SessionManager` (hand-rolled JSONL, one entry per whole message) plus `AgentSession`, which subscribes to the bare `Agent`'s event stream and calls `sessionManager.appendMessage()` on `message_end` — exactly the "aggregate a live event stream into your own persisted shape" approach ADR-0006 already rejected twice (for opencode and for Claude) in favor of re-deriving from the backend's own authoritative transcript (ADR-0007's `getSessionMessages` approach). The map's premise was adopting pi "as just a tool-calling loop" (`pi-agent-core` + `pi-coding-agent`'s tool factories); getting working persistence/resume in practice means either hand-rolling the same event-aggregation bridge `pi-coding-agent` already wrote (ADR-0006's rejected approach, a second time), or depending on much more of `pi-coding-agent`'s own opinions — its CLI/TUI product, not just a library — than the map intended. Resume is also file-path-keyed (`SessionManager.open(path)`/`continueRecent(cwd)`), not opaque-id-keyed like Claude's `resume: session.agentSessionId`; dilna would have to persist and track a `.jsonl` file path per session itself, and `continueRecent`'s "most recently modified file for this cwd" heuristic doesn't fit dilna's model of potentially several sessions per worktree over time.

## Why not a narrower option

**Hybrid (keep `claude-agent-sdk` for Anthropic, add `pi.ts` only for future non-Anthropic providers) was considered and rejected too**, not just full replacement. It would sidestep problem #1 (Anthropic keeps its current billing), but problems #2 and #3 are properties of the pi stack itself, not specific to using it for Anthropic — a `pi.ts` adapter for DeepSeek or any other provider would carry the same unconfined read/edit/write tools and the same "build your own persistence bridge" cost. It would also reopen the exact "two adapters for how many active backends" tension ADR-0011 dropped opencode over — ADR-0011 itself said that calculus changes "once multi-provider is an actual GA requirement rather than speculative capacity," but no concrete provider requirement (an actual DeepSeek user request, say) exists today; the GA plan's want for broader provider support remains speculative capacity, the same condition ADR-0011 already weighed against.

## Consequences

- Map [#87](https://github.com/MrMarble/dilna/issues/87) is closed by this decision; both its child tickets (#90, #91) and this one are resolved, and nothing remains on that map's frontier.
- `docs/research/pi-agent-harness.md` (branch `research/pi-agent-harness`) and the spike at `/home/atm/Documents/repos/pi-sandbox-spike` (branch `main`, commit `f9c1d4a`, local only — not pushed to GitHub) are kept as-is, unmerged, as the primary sources behind this ADR's findings. Don't delete or merge them; re-read them directly if this decision is ever revisited.
- The three friction issues that partly motivated this evaluation (#70, #74, #83) are already closed and already fixed within `claude-agent-sdk` itself (ADR-0010's Follow-ups 1, 3, 4) — this ADR doesn't reopen them, it just declines to address them by changing backends.
- dilna still has exactly one agent backend. Multi-provider support (DeepSeek etc.) remains unbuilt. If a concrete provider requirement shows up later, it needs its own fresh evaluation — of the pi stack (if newer versions have fixed the gaps above) or of alternatives — not a resumption of map #87, which is closed.
- No code changes: `apps/server/src/agents/claude.ts` and every other adapter file are untouched.
