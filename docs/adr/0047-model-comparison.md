# Model comparison: N ordinary Sessions sharing a group id

Issue #250 asks for one prompt run against N models with the outputs readable side by side. The central design question is what an "arm" is. We decided: **a comparison is N ordinary Sessions grouped by a nullable `sessions.comparisonGroupId`** — not a new entity above Session. Every existing invariant keeps holding verbatim: one worktree and branch per arm, one SSE subscription per arm, per-arm cost/token accounting, idle-kill, notifications, transcript rendering. A `comparisons` parent table with child arms that aren't full Sessions was rejected because it forks the lifecycle (a second turn-execution path, persistence story, status model, and idle-kill surface) for no capability the view needs — the same "adapter + dispatch branch, not a new abstraction layer" reasoning as ADR-0011. The shared prompt is not modelled at all: it is already persisted as each arm's first user message.

`POST /api/comparisons` (`{ repoId, prompt, models: [{provider, model}, …] }`) is the one fan-out entry point: it creates the arms with caller-chosen provider/model (validated against the same provider catalog + API-key check the Settings override uses, so the DB can't hold a combination the agent startup path couldn't resolve), then runs the prompt on each arm through the existing `beginTurn`/`runTurn`/`trackRunningTurn` path. `SessionManager.create` gained optional provider/model overrides for the same reason (the "create a Session on a specific model" primitive the instance-default path couldn't express).

The view is a route (`/compare/<groupId>`, "compare" added to the reserved slugs) rendering the existing `ChatShell`s side by side on desktop; below the breakpoint it renders one column at a time with a pill toggle above the composer to switch the active arm. There is deliberately **no group-send endpoint**: each arm's `ChatShell` keeps its own composer, so a follow-up prompt goes to the arm (or arms) the user types into — matching the mobile pill's "select the active model" contract. Arms are normal agentic Sessions, not inspect-only: the harness is part of what's being compared. Scoring/ranking of arms, blind presentation, and promoting a winner's worktree are all out of scope (v1); the per-arm cost totals already land in the Metrics view through ordinary usage accounting.
