# Sandbox the Claude backend via Claude Code's own built-in Bash sandbox

ADR-0003 justified auto-approving every tool call ("no per-tool approval, the stop button is the manual override") on the assumption that "the agent runs in an isolated docker container with no host access, so the blast radius is the worktree only." That isolation was never actually built — `startOpencode`/`startClaude` just called `child_process.spawn()` on the host, with `cwd` set to the worktree as a convention, not a boundary. An agent could (and, during dogfooding, did) write outside its assigned worktree — in the observed incident, into dilna's own live checkout — via an absolute path or a `bash` tool call. A second dogfooding session then showed the same gap on the read side: asked about its own working directory, an agent walked up its own worktree's ancestor directories, read dilna's own `CLAUDE.md`, and used it to reason about a project it had no business seeing at all.

## Decision

`apps/server/src/agents/claude.ts`'s `startClaude` enables Claude Code's own built-in sandbox (the same mechanism behind the CLI's `/sandbox` command) via the Claude Agent SDK's `options.sandbox` and `options.settings.claudeMdExcludes`, rather than wrapping the whole `claude` process externally (see "Prior approaches" below for why two external-wrapper attempts were abandoned):

- `sandbox.enabled: true` + `autoAllowBashIfSandboxed: true` + `failIfUnavailable: true` — every Bash command runs sandboxed and auto-approved (matching ADR-0003's no-per-tool-approval model); if the sandbox's own dependencies (`bubblewrap`, `socat` on Linux) are missing, `query()` fails loudly instead of silently running unsandboxed.
- `sandbox.filesystem.allowWrite`: Claude's own cache/transcript/session-scratch directories (`~/.cache/claude`, `~/.cache/claude-cli-nodejs`, `~/.claude/session-env`, `~/.claude/projects`, `/tmp/claude-<uid>`) — not project files — plus the worktree's shared git dir (objects, refs, config), resolved the same way as the read side below (`resolveGitCommonDir`). The worktree itself is writable automatically. This ADR originally assumed the sandbox's git-worktree awareness also auto-grants write to the main repo's shared `.git` dir for `git commit` etc., matching what was observed testing the SDK in isolation (see Verification); real dilna sessions — worktrees living under `DILNA_DATA_DIR`, backed by a bare repo elsewhere rather than a conventional sibling `.git` — showed that auto-grant doesn't fire, so `git commit`/`git branch` failed "Read-only file system" until dilna started resolving and passing that path itself, same as it already did for `allowRead`.
- `sandbox.filesystem.denyRead` / `allowRead`, **only when `DILNA_DATA_DIR` resolves inside dilna's own checkout** (detected by walking up from `claude.ts`'s own location for `pnpm-workspace.yaml`, same check as the abandoned sandlock approach used): deny read on the checkout root, re-allow only the current worktree and its repo's shared git object store (resolved via `resolveGitCommonDir`, kept from the old `sandbox.ts` for this). Unlike sandlock, this parent-deny/nested-child-allow pattern is supported and verified working (see Verification below) — no sibling enumeration needed, since denying the whole ancestor and re-opening one nested path already excludes every sibling session/repo as a side effect.
- `settings.claudeMdExcludes`, same condition: excludes `<checkout-root>/CLAUDE.md` and `<checkout-root>/**/CLAUDE.md` from Claude Code's own project-memory auto-discovery (which walks up from `cwd` at session start looking for `CLAUDE.md` files) — this is the direct fix for the second incident above, which `denyRead` alone does not cover (memory loading isn't a Bash-tool file access).
- `sandbox.network.allowedDomains: ["*"]` — no domain is pre-allowed by default, and Claude Code prompts for approval the first time a command needs a new one; with no human present in dilna's headless sessions, that prompt would just hang forever. Allowing all domains matches the previous sandlock config's unconditional `--net-allow '*'` (agents need arbitrary outbound access — LLM APIs, git remotes, whatever they're asked to fetch — none of which is enumerable in advance).
- `sandbox.enableWeakerNestedSandbox`, gated on a new `DILNA_CONTAINERIZED=true` env var (set only in dilna's own `Dockerfile`): bubblewrap can't mount a fresh `/proc` inside an already-unprivileged container, so this makes it bind-mount the container's existing one instead. Only safe when an outer container already provides the real isolation boundary — true for dilna's own container, not for bare-host dev, hence the env-var gate rather than a blanket default.

## Prior approaches: bubblewrap, then sandlock — both abandoned

**bubblewrap (bwrap), wrapping the whole process externally** was the first implementation. It worked cleanly on a bare host, but doesn't fit dilna's Docker/Kubernetes deployment target (ADR-0009): creating a new mount namespace and calling `pivot_root` needs `CAP_SYS_ADMIN` plus disabling both seccomp *and* AppArmor entirely inside the container.

**[sandlock](https://github.com/multikernel/sandlock), wrapping the whole process externally**, was adopted next specifically to avoid that: Landlock + seccomp-bpf instead of mount namespaces, needing only a narrow `SYS_PTRACE` capability. This worked for write confinement, but two problems surfaced:

- Read confinement (denying dilna's own checkout, re-allowing the worktree) requires `--fs-deny`. *Any* `--fs-deny` rule at all, regardless of which path it names, makes the Claude Agent SDK's own CLI binary (`@anthropic-ai/claude-agent-sdk-linux-x64`, a **Bun-compiled binary**) exit immediately with code 1 and zero output. Confirmed by bisection: a single irrelevant `--fs-deny` path breaks a bare `claude --version` the same way the full rule set does, while the identical sandlock invocation with `echo` in place of `claude` succeeds. This was reverted (read confinement dropped, write-only kept) before the problem below was found.
- Worse, discovered only once real usage was dogfooded: sandlock wrapping the top-level `claude` process breaks **the Bash tool itself**, unconditionally — not just under `--fs-deny`. Claude's own Bash tool implementation works by spawning a nested child process from within the already-sandboxed top-level process; that nested spawn fails silently (exit 1, no stdout/stderr) under sandlock, exactly like the `opencode`-specific nested-spawn quirk this ADR previously documented as a known, low-priority, opencode-only limitation — except it turns out to affect the Claude backend too, because the actual binary sandlock supervises (`claude-agent-sdk-linux-x64`) is *also* Bun-compiled, not "a plain Node process tree" as this ADR previously (incorrectly) assumed. Confirmed independent of dilna's own code: a bare `claude -p "..."` wrapped only in `sandlock run -r / -w <dir>` (no `--fs-deny`) reproduces the same total Bash-tool failure. No matching upstream issue found in sandlock's or Bun's issue trackers.

Both external-wrapper approaches share the same fatal shape: wrapping the *entire* Bun-compiled `claude` process from outside puts every subprocess it spawns internally (including its own Bash tool) one nesting level deeper inside somebody else's sandbox, which this class of tool doesn't handle. Claude Code's built-in sandbox avoids this because it invokes bubblewrap itself, per Bash command, from inside the CLI process — there is no external nesting to trip over.

Both external-wrapper approaches were chosen over a container-per-session at the time: the reported problem concerned filesystem writes, not process/network isolation, and a per-session container would need the dilna server itself to reach a Docker daemon — a much bigger dependency shift. That reasoning still holds; a container-per-session was not reconsidered as part of this change.

Claude Code's built-in sandboxed Bash tool itself was actually already known when sandlock was adopted, and rejected then on the reasoning that "Read/Edit/Write tool calls are governed by Claude's own permission rules instead of an OS boundary... it would not have prevented either incident, since neither was necessarily a Bash call." That reasoning was incomplete: it didn't account for `claudeMdExcludes`, a separate, purpose-built option for exactly the CLAUDE.md-loading incident, found only once the sandlock approach's failure forced a closer look at Claude Code's own sandboxing docs.

## Verification

Verified live, directly against the SDK (outside dilna's own code, to isolate the mechanism from dilna's wiring), after installing the sandbox's Linux dependencies (`bubblewrap` — already present on the dev host; `socat` — installed via `pacman`):

1. **Bash tool works** with `sandbox.enabled: true` — unlike sandlock, which broke it unconditionally.
2. **Write confinement holds**: a command writing outside the worktree fails with "read-only file system".
3. **Read confinement holds, including the parent-deny/nested-child-allow pattern sandlock could not do**: `filesystem.denyRead: [checkoutRoot], allowRead: [worktree]` — reading a file outside the worktree via Bash (`cat`) fails with "No such file or directory".
4. **The original second incident, reproduced and fixed**: with a worktree nested inside a fake checkout root and no `claudeMdExcludes`, the agent's own project-memory context contains the fake checkout's `CLAUDE.md` content (confirmed via a direct question, with a negative control showing it's absent when `claudeMdExcludes` targets that path).
5. **Headless network access works without hanging**: `network.allowedDomains: ["*"]` lets a Bash command reach a domain it's never used before in-session, with no approval prompt (which no human is present to answer in dilna's headless sessions).
6. ~~Git worktree write access to the shared object store is granted automatically, without dilna needing to compute and pass it itself.~~ Not reproduced in real dilna sessions — see "Consequences" below; dilna resolves and grants this path itself, same as the read side.

**Not verified**: `enableWeakerNestedSandbox` inside dilna's actual Docker image / a real Kubernetes pod. Bubblewrap's behavior inside an unprivileged container (whether the container/pod's own `securityContext` needs additional capabilities or a relaxed seccomp/AppArmor profile beyond what `enableWeakerNestedSandbox` alone provides) could not be checked from this development environment and remains the user's responsibility to verify before relying on it in production.

## Consequences

- Dilna's own container image needs `bubblewrap` and `socat` (both ordinary Debian packages via `apt-get`, unlike sandlock which had to be fetched as a prebuilt release binary) instead of `sandlock`.
- Read confinement is meaningfully better than either prior attempt: the parent-deny/nested-child-allow pattern works, and the specific CLAUDE.md-loading incident has a dedicated fix. It still only covers Bash-tool-mediated file access (and project-memory loading, via the separate `claudeMdExcludes` option) — Read/Edit/Write tool calls remain governed by Claude's own permission system, which dilna bypasses entirely (`permissionMode: "bypassPermissions"`, ADR-0003). This gap is unchanged from every prior approach, not a new regression.
- This doesn't sandbox process visibility (no PID namespace) or meaningfully restrict outbound network access (`allowedDomains: ["*"]`, intentionally, per above) — an agent could still, in principle, signal unrelated host processes it has permission for, or exfiltrate data over the network. Full defense-in-depth (PID namespaces, egress allowlisting) is a larger follow-up, not required by the reported incidents.
- `enableWeakerNestedSandbox` is gated on `DILNA_CONTAINERIZED=true`, set only in the `Dockerfile` — bare-host dev keeps the stronger, non-weakened sandbox since it has no outer container providing isolation.
- opencode's nested-spawn quirk, previously documented here as an open opencode-only limitation, no longer applies: opencode was dropped as a backend (ADR-0011), and the mechanism behind it turned out to also explain the more severe Claude-backend sandlock failure this ADR now describes.
- The claimed automatic write grant for a linked worktree's shared git dir (Decision/Verification item 6, both struck through above) does not hold for dilna's own worktree topology (checkout under `DILNA_DATA_DIR`, git-dir under a separate bare-repo root rather than a conventional sibling `.git`) — every git-mutating command (`commit`, `branch`, etc.) failed "Read-only file system" in real sessions. Fixed by having `claude.ts` resolve and pass `gitCommonDir` to `filesystem.allowWrite` itself, mirroring the `allowRead` handling it already had.

## Follow-up: closing the `dangerouslyDisableSandbox` escape hatch (issue #74)

Claude Code's Bash tool accepts its own `dangerouslyDisableSandbox` parameter, letting a single command opt itself out of the bwrap confinement above entirely. The SDK honors it by default. Combined with `bypassPermissions` (ADR-0003, no human present to approve or deny a tool call), an agent could set that flag on its own initiative with nothing to stop it — and did, in a self-hosting session working on dilna's own repo, when `mise`/`pnpm` toolchain setup hit a writability gap the existing `*_WRITABLE_PATHS` grants didn't cover. The resulting unsandboxed commands left host-style dotfiles (`.bashrc`, `.zshrc`, `.gitconfig`, `.idea`, `.vscode`, `.mcp.json`, `.claude/*`) scattered in the worktree — never committed, but a real illustration of the blast radius: the "Consequences" section above already flagged that Read/Edit/Write bypass the sandbox by design, but this is the same problem for Bash, and unlike the Read/Edit/Write gap, it has a direct fix.

Fixed by setting `settings.sandbox.allowUnsandboxedCommands: false` in `claude.ts`'s `query()` options, which makes `dangerouslyDisableSandbox` a no-op instead of honoring it. This trades away a fallback for genuine future writability gaps (an agent that hits one now fails outright rather than working around it) — accepted deliberately: per ADR-0003, `bypassPermissions` is only safe *because* the sandbox is airtight, so the correct response to a real gap is widening the relevant `allowWrite` grant, not giving the agent a way to opt itself out of confinement. `DILNA_AGENT_CONTEXT` was also updated to tell the agent the sandbox can't be disabled and that no state (including `$HOME`) persists between separate Bash tool calls, since the latter was the actual pressure that pushed the agent toward the escape hatch in the first place.
